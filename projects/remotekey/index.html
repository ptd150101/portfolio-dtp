01 · Problem

A remote desktop session that cannot use desktop shortcuts feels incomplete.

Physical Bluetooth and USB keyboards usually type correctly through Android remote desktop apps. The failure appears around operating-system shortcuts: Android or vendor firmware can intercept Alt + Tab, Windows + E and Windows + Tab before the remote app can forward them to the Windows PC.

RemoteKey does not stream the screen, replace Parsec or relay every keystroke. It supplies only the missing shortcut path.
Native path

Normal typing

Physical keyboard → remote desktop app → Windows. No extra connection, no duplicate input and no added hop.

Recovery path

Selected shortcuts

Physical keyboard → Android AccessibilityService → TCP agent → Win32 SendInput.

02 · Architecture

A two-ended system with a deliberately small protocol.

Physical keyboard

Produces Android key events while a remote desktop or remote gaming client has focus.

AccessibilityService

Requests physical key filtering, tracks modifiers and intercepts only explicitly supported system combinations.

Relay worker

Serializes key events as JSON Lines, performs token handshake, maintains a bounded queue and reconnects in the background.

Windows TCP agent

Authenticates one client, validates packet type and protocol version, and guarantees key release on disconnect.

Key mapper

Maps Android key codes to Windows virtual keys and marks extended keys correctly.

Win32 injector

Calls MapVirtualKeyW and SendInput using correctly sized native structures.

The architecture can run on the same LAN or through a trusted private VPN such as Tailscale. Video, audio, mouse and normal keyboard input remain the responsibility of the existing remote application.

03 · Core decision

Relay only what the native route cannot deliver.

Forwarding every key through a second TCP connection would create a new keyboard system beside the one already built into the remote app. That would introduce avoidable latency, duplicate keystrokes, ordering problems and conflicts around text editing or international input.

Event handling policy

The system complements the remote application instead of competing with it. That makes the simplest path the fastest path.
04 · State machine

Key-down and key-up ordering must survive interruptions.

The Android service keeps separate state for modifiers currently held by the user, modifiers already relayed to Windows and combo keys that are active. This prevents repeated modifier-down events and ensures each key-up is paired with the path that originally handled its key-down.

Service interrupt · capture disabled · settings changed · socket disconnect · emergency chord → RELEASE_ALL

Emergency stop

Ctrl + Alt + Shift + F12 disables capture, clears Android shortcut state and requests a remote key release. It is designed as a recovery mechanism when a vendor, device or network behaves unexpectedly.

Queue overflow recovery

The relay uses a bounded 2,048-message queue. If it fills, the client clears queued state, marks the connection for resynchronization, inserts release_all and then keeps the newest event. Losing old transient input is safer than preserving an inconsistent modifier state.

05 · Protocol

Readable on the wire, strict at the boundary.

RemoteKey uses newline-delimited JSON over TCP. The format is intentionally easy to inspect with a test client, while the server still validates authentication, protocol version, packet size, event action and key code.

{"type":"key", "action":"down", "keyCode":57}
{"type":"key", "action":"down", "keyCode":61}
{"type":"key", "action":"up", "keyCode":61}
{"type":"key", "action":"up", "keyCode":57}
{"type":"release_all"}
Handshake

Token + protocol version

Rejects accidental clients and prevents incompatible client/server versions from silently exchanging events.

Connection policy

One active client

A non-blocking lock prevents two Android devices from injecting overlapping modifier state.

Idle behavior

Ping packets

Detects dead connections and keeps the socket active without generating keyboard input.

Safety

Release on every boundary

The agent releases tracked keys after handshake, on explicit request and in the disconnect finally path.

06 · Windows agent

Python at the boundary of native Win32 input.

The agent uses only the Python standard library at runtime. It maps Android key codes to Windows virtual keys, records pressed keys under a lock and emits native keyboard input through ctypes.

Native details that matter

  • Extended keys such as Windows, right Alt, arrows and Numpad Enter receive KEYEVENTF_EXTENDEDKEY.
  • MapVirtualKeyW derives the scan code associated with each virtual key.
  • The INPUT and KEYBDINPUT structures use pointer-sized dwExtraInfo, avoiding incorrect 64-bit structure sizing.
  • The injector tracks pressed Android key codes and releases them in reverse order.
  • --dry-run exercises the server and protocol without injecting real Windows input.

Distribution

A one-command build produces a debug Android APK and a standalone Windows executable with launchers, configuration, firewall setup and logging. The target PC does not need Python installed when using the packaged agent.

07 · Testing

Protocol behavior can be verified without a tablet or real key injection.

The test suite imports the agent, replaces the native injector with a recording implementation, starts the TCP server on a temporary local port and sends a real authenticated session through a socket.

Test client

Connects to a temporary server address and sends a protocol v1 hello packet with a known token.

Agent server

Authenticates the client and returns a successful hello response.

Alt + Tab sequence

Sends Alt down, Tab down, Tab up and Alt up as four individual packets.

Recording injector

Asserts that the final event list exactly matches the expected order.

Additional test coverage

Unit tests verify common Android-to-Windows mappings, letter and number ranges, function keys and the extended-key status of Numpad Enter.

The design keeps protocol testing independent from Win32. Native injection is the final adapter, not a requirement for exercising server state.
08 · Security & limits

Useful within a trusted network, deliberately not presented as an Internet relay.

BoundaryCurrent behavior
TransportUnencrypted TCP. Use only on a trusted LAN or private VPN.
AuthenticationShared token compared with hmac.compare_digest.
Client countOne active client; additional clients are rejected.
Packet sizeMaximum line size is 64 KB.
Windows securityCannot generate Ctrl+Alt+Delete or bypass the secure UAC desktop.
Android firmwareSome vendors consume Meta/Windows before AccessibilityService receives it.

Honest product boundary

Administrator mode can help control ordinary elevated applications, but it does not bypass Windows secure desktop. Likewise, no software-only AccessibilityService can recover a key event that device firmware never delivers to Android applications.

09 · Next iterations

Reduce setup friction and strengthen the pairing boundary.

Random pairing token and QR configuration

Generate a new token on first agent launch and let the Android app scan IP, port and token instead of typing them manually.

Optional encrypted transport

Add TLS or a short-lived pairing challenge for users who cannot rely on an already encrypted private VPN.

LAN discovery and Windows tray UI

Advertise the agent on the private network, show status in a tray application and make firewall or administrator state visible.

Shortcut profiles

Allow users to opt into additional combinations while preserving the shortcut-only principle and conflict validation.

Compatibility matrix and instrumentation

Measure LAN latency, reconnect time and device/firmware support across tablets and remote applications.

The system is intentionally narrow. Future features should improve pairing, compatibility and observability without turning it into a second full keyboard stack.
